# 布娃娃交互审计与重构建议

检查日期：2026-11-07。对象：`res://scenes/test/corpse_interaction_sandbox.tscn` 及其角色控制器、家具和现有验收脚本。实测环境：项目当前 Godot 4.7.2、Jolt、默认 60 Hz 物理步长。

> **最新复查：骨骼绑定已修正，当前实测为 16/16 有效且参与模拟。** 用户反馈的“现在太软、不成人形”属于下一阶段的关节范围、碰撞包络及自碰撞配置问题。请优先阅读本文第 8 节；第 1–7 节保留首次检查的历史证据，其中“只有骨盆有效”、旧胶囊尺寸、整链速度传播和 Y=0 等描述对应修正前版本，不能直接当成当前状态。

## 结论与处理决策

**首次检查时，没有正常运行一套完整的关节布娃娃：创建了 16 个 PhysicalBone3D，但原始场景运行时只有 Hips 成功绑定并参与模拟，其余 15 个的骨骼 ID 都是 -1。** 用户当时感到“整个身体像一块刚体旋转”，有明确的实现原因。此项已在后续修改中修正，见第 8 节。

保留 `Skeleton3D + PhysicalBoneSimulator3D + PhysicalBone3D + Jolt` 路线，局部重构物理骨架创建、拖拽和状态切换，并重做相关验收。无需重写整个项目，也没有证据支持先换物理引擎。布娃娃本来就可以由普通刚体和关节组成；“柔软”的感觉来自多个部位之间的相对运动，并不要求 SoftBody3D。单个 RigidBody3D 会保持整体形状，换成一个普通刚体反而不能满足目标。[Godot 布娃娃教程](https://docs.godotengine.org/en/stable/tutorials/physics/ragdoll_system.html)、[RigidBody3D](https://docs.godotengine.org/en/stable/classes/class_rigidbody3d.html)

没有找到可据以还原最初设计决策的独立计划文件，不能断言原计划全部错误。现有源码的目标是多部位物理，但节点组织错误；此外，拖拽和固定姿势路径也与“始终受碰撞约束的柔软身体”不一致。仅继续调整摩擦、阻尼或增加地面推力，无法修复这些问题。

本次只做调查、运行验证和文档记录，没有保存任何运行逻辑修改。下述修复方案尚未实施。

## 1. 已复现的核心故障

位置：[corpse_ragdoll_controller.gd，第 58 行](<D:/Prism Route/prism-route/scripts/characters/corpse_ragdoll_controller.gd:58>)，尤其是第 135–143 行。

当前创建方式把 Hips 放在模拟器下面，其余物理骨骼又按人体层次嵌套到上一个 PhysicalBone3D 下面：

```text
Skeleton3D
  PhysicalBoneSimulator3D
    PB_Hips
      PB_Spine
        PB_Chest
          PB_Head
          PB_LeftUpperArm ...
      PB_LeftUpperLeg ...
```

在当前版本与实现中，嵌套部分没有成功绑定。场景启动约 2 秒后检查每个节点的 `get_bone_id()` 和 `is_simulating_physics()`，结果如下：

| 检查项 | 原始场景 | 仅在内存中改成模拟器直接子节点后 |
| --- | ---: | ---: |
| 创建的 PhysicalBone3D | 16 | 16 |
| 模拟器直接子节点 | 1 | 16 |
| 骨骼 ID 有效的物理骨骼 | 1 | 16 |
| 实际参与物理模拟的物理骨骼 | 1 | 16 |
| 无效骨骼 | 除 Hips 外全部 15 个 | 无 |

原始 Hips 的 ID 为 2；其余均为 -1，且不在模拟。对照操作是在独立诊断进程中停止模拟、将全部 PhysicalBone3D 以保留全局变换的方式重新挂到模拟器下面，再启动模拟并等待约 2 秒。没有保存场景或修改控制器文件。

这个对照足以确认节点组织是首要故障，但**不能把 16/16 绑定成功等同于最终布娃娃已经调好**。关节朝向、活动范围、碰撞包络和拖拽还需分别处理。官方教程采用模拟器管理物理骨骼的结构；绑定有效性应通过 API 检查，不能只看节点数量或模拟器整体的开关状态。[官方结构说明](https://docs.godotengine.org/en/stable/tutorials/physics/ragdoll_system.html)、[PhysicalBone3D 绑定与模拟 API](https://docs.godotengine.org/en/stable/classes/class_physicalbone3d.html)

目标节点结构应为：

```text
Skeleton3D
  PhysicalBoneSimulator3D
    PB_Hips
    PB_Spine
    PB_Chest
    PB_Head
    PB_LeftUpperLeg ...（其余全部同级）
  VRMSpringBoneSimulation（另行限定头发、服饰骨骼）
```

人体连接关系由 Skeleton3D 的骨骼关系、物理骨骼绑定与关节坐标系表达，不用物理节点相互嵌套表达。修复时也要相应重算模拟器坐标下的变换，不能只删除 `parent_pb.add_child()` 而保留原来的父骨骼局部变换。

## 2. 拖动为什么像整体平移、整体转动

### 2.1 物理拖拽在同时驱动整条父级链

位置：[控制器，第 210 行](<D:/Prism Route/prism-route/scripts/characters/corpse_ragdoll_controller.gd:210>)。

当前先把被抓部位的线速度插值到目标速度，再遍历所有 PhysicalBone3D 父节点，逐级把它们也拉向同一个目标。它不是只在一个接触点施力、让关节自然传递受力。当前脚部本身尚未有效模拟，但这段父级遍历能一路写到 Hips，因此“拖脚后骨盆移动”的测试仍能通过。

即使绑定修正，这种多部位速度牵引仍会压低局部摆动，使身体过于同步；固定的每步插值比例也没有使用传入的 delta。节点改成同级后，原来的父级遍历将失去原有意义，必须一起重做，而不是再次嵌套物理节点来迁就它。

建议只约束实际抓取点：记录命中的刚体及其局部命中坐标，通过抓取约束或受限弹簧阻尼力追随目标。考虑抓取点速度、转动影响、最大力及目标加速度，让其余部位由关节响应。Godot 对频繁直接修改刚体变换或速度有明确注意事项，推荐在物理状态积分阶段控制。[RigidBody3D 控制说明](https://docs.godotengine.org/en/stable/classes/class_rigidbody3d.html)

### 2.2 POSED_DRAGGING 本来就是整模移动

位置：[控制器，第 232 行](<D:/Prism Route/prism-route/scripts/characters/corpse_ragdoll_controller.gd:232>)、[第 259 行](<D:/Prism Route/prism-route/scripts/characters/corpse_ragdoll_controller.gd:259>)。

应用预设姿势时会停止布娃娃模拟；后续拖拽直接修改 `character_instance.global_position`，保持根节点高度并增加少量整体摇摆。这是固定姿势模型平移，没有对整个模型做运动扫掠或物理接触求解。它不能作为柔软布娃娃的实现或验收依据。

模式切换还会把角色根节点直接放到 `(hip.x, 0, hip.z)`。它把世界 Y=0 当成所有支撑面，放到床、桌子、台阶或斜坡上自然不成立。应明确区分“编辑/摆姿预览”和“受物理约束的身体交互”。如以后需要维持目标姿势同时保留接触，应另做关节目标驱动；本轮优先完成被动物理，不必立即开发完整 active ragdoll。

## 3. 穿地与家具穿模：已知原因和证据边界

### 3.1 地板碰撞存在，不能靠骨骼原点判断穿模

沙盒地板为 60×2×60 的 BoxShape3D，中心 Y=-1，顶面恰好 Y=0；可见地板也在 Y=0。它有实体厚度，当前没有发现“只有可见平面、根本没有地面碰撞”的问题。

当前防穿地逻辑位于[控制器第 196 行](<D:/Prism Route/prism-route/scripts/characters/corpse_ragdoll_controller.gd:196>)：当某个骨骼原点低于 0.04 米且向下运动，就把其竖直速度改成 +0.2。这个判断没有使用碰撞形状底部、实际接触面或网格轮廓；原点在地上不代表身体在地上。它也无法应对家具高度，还会在接触求解之外持续注入向上速度，可能造成抖动。

原始场景约 2 秒时，Hips 原点 Y≈0.09992，其胶囊最低点约为 -0.00008；RightFoot 原点约 -0.00670，其形状最低点约 -0.00761，且该脚没有参与模拟。仅在内存中修正绑定后，部分手、脚胶囊仍出现约 2 厘米的瞬时底部越界，说明**修复绑定是必要步骤，尚不足以验收接触质量**。

这些数值是变换后的胶囊几何边界，不是渲染蒙皮穿透深度，也不是长期稳定误差统计。本次没有得到足以定量宣称“可见身体穿地多少厘米”的完整蒙皮测量。后续需观察稳定后的多帧接触，同时检查最终蒙皮，而不是把一个瞬时数值当成全面结论。

### 3.2 碰撞体尺寸存在自动收缩，不能只相信配置表

代码先设置 capsule.radius，再设置 capsule.height。胶囊 height 包含两个半球，必须至少为半径的两倍，不满足时属性会自动调整。[CapsuleShape3D 尺寸规则](https://docs.godotengine.org/en/stable/classes/class_capsuleshape3d.html)

例如当前 Hips 配置 radius=0.11、height=0.20，最终半径为 0.10；Spine/Chest 配置 0.10、0.16，最终半径为 0.08，Head 的 0.09、0.16 同样受限。这会使实际支撑包络小于仅看源码半径所期待的尺寸。

腿部固定胶囊高度为 0.34 米，实测相应骨段端点间距约 0.398/0.417 米；这提示需要检查端部覆盖与接缝，但不能仅凭长度差就判定所有部位一定穿模。抽查的手臂、腿部胶囊轴向大体与骨段一致，没有证据支持把问题概括为“所有胶囊都朝错方向”。

应按角色的静止骨架和可见轮廓拟合躯干、头、四肢、手脚，检查最终属性及 body_offset、joint_offset。接触身体主要表面需要合理厚度，不能期待很细的骨段胶囊自动撑起外扩衣裙或头发。

### 3.3 关节和碰撞过滤尚不足以支持自然效果

- 膝、肘目前使用 PIN，允许球窝式转动；没有显式配置符合人体的弯曲轴及角度限制。修复绑定后应优先检查膝肘铰链、肩髋锥形范围和关节坐标系，避免反折、扭转及初始约束冲突。
- 当前 `collision_layer=4` 的位值实际是第 3 层，源码注释“Layer 4”不准确；`mask=1|2` 包含第 1、2 层。地板、床、桌实际在第 1 层，因此不能仅凭注释认定它们不碰撞。
- 该 mask 没有包含身体自身所在的位值 4，身体部位之间被整体排除。后续可按需要允许非相邻部位接触并排除相邻关节，不宜直接开启全部自碰撞，造成原本交叠的相邻胶囊相互顶撞。
- 床垫顶面约 Y=0.46，桌面顶面约 Y=0.84。硬编码 Y=0 的模式切换和“地板缓冲”显然不能替代这两种家具接触。

### 3.4 服饰/头发是另一层问题

该角色运行时同时存在活动的 PhysicalBoneSimulator3D 和 VRMSpringBoneSimulation。不能仅凭两个修改器都启用，就认定它们争抢同一骨骼；需要明确身体骨骼与服饰/头发骨骼的控制范围、执行顺序以及环境碰撞设置。

身体胶囊不穿地，不代表裙摆、发梢也不会穿地。服饰弹簧也不会因为附近存在 StaticBody3D 就自动获得符合预期的环境碰撞。先验收身体，再接入衣发环境碰撞与必要的稳定性限制。

读取最终受修改器影响的骨骼姿势时，应在对应 `modification_processed` 信号时读取，避免把修改器处理之外的基础姿势误当成渲染最终姿势。[SkeletonModifier3D 姿势读取时机](https://docs.godotengine.org/en/stable/classes/class_skeletonmodifier3d.html)

## 4. 为什么现有测试会全部通过

本次运行了现有 [verify_corpse_sandbox.gd](<D:/Prism Route/prism-route/tools/verify_corpse_sandbox.gd>)，现有 6 项检查全部通过，但此时依旧只有 1/16 个有效物理骨骼。

它检查节点/UI、状态切换、骨盆拖动位移、脚膝距离、预设姿势切换及整模平移。防穿模只检查短暂等待后的 Hips/LeftFoot **节点原点**是否高于 0.02 米。它没有验证各物理骨骼绑定、各部位真正进入模拟、关节实际弯曲、碰撞体/蒙皮底部或家具接触。原测试在拖动时还直接平移玩家，不能代表完整的玩家碰撞交互。

因此，“6 项通过”只说明这些状态和位移条件成立，不支持其输出中“布娃娃拖拽已完全验证”的结论。后续直接增强这一个现有脚本，复用本沙盒；不再增加平行测试场景、截图组或独立报告目录。

## 6. 建议的有限重构顺序

1. **先让完整身体真正进入模拟。** 所有物理骨骼置于模拟器直接子层，重算变换并验证 16/16 有效绑定和模拟。显式记录预期的 15 条身体连接；不通过就阻止交互验收继续。
2. **单独做好被动落地。** 拟合碰撞包络，配置关节轴向、限制及质量分布，取消按世界 Y 写速度的缓冲。先关闭拖拽，只验证地板、床、桌、边缘与斜面接触；正确接触后允许稳定休眠，抓取时唤醒。
3. **替换拖拽实现。** 物理射线获得真实命中刚体和局部抓取点，检查遮挡；使用一个受限抓取约束或阻尼弹簧，不再给整条链改速度。限制目标突变、力和速度，释放时保留合理动量。持续作用按物理步处理，避免每步施加相同固定冲量造成步频依赖。
4. **整理状态边界。** 被动、抓取保持真实模拟；预设姿势编辑明确作为独立模式。模式切换保留正确世界位姿，并基于实际支撑面处理高度，删除世界 Y=0 假设。暂不把复杂姿势驱动作为第一阶段前置条件。
5. **接入衣发二级物理。** 确认骨骼控制范围后，再设置环境碰撞、稳定性及性能预算。主体接触和服饰贴合分别验收。
6. **增强现有验收并在原场景交付。** 更新现有验证脚本的断言含义，保留原场景入口。先单角色完成，再按角色身材复用/调整物理配置，不立即为数十个角色手工复制一套脚本。

这些工作主要集中在控制器、角色物理配置和现有验证脚本；无需改动主世界地图、动画库、材质系统或 MMD 重定向链路。

## 7. 后续验收标准

| 项目 | 必须看到的结果 |
| --- | --- |

| 物理步频 | 固定正常物理步频先通过，再检查不同渲染帧率下手感是否一致；必要时做有限步频对照 |

## 8. 第二次复查：绑定修好后过度柔软、折叠失形

### 8.2 搜索所得：活动范围、阻尼、姿势驱动是三种不同控制

- **活动范围**决定“允许折到哪里”。PIN 约束连接点，允许自由旋转；膝肘需要明确弯曲轴和限角，肩髋及颈椎需要分别限制摆动与扭转。[PinJoint3D](https://docs.godotengine.org/en/stable/classes/class_pinjoint3d.html)、[HingeJoint3D](https://docs.godotengine.org/en/stable/classes/class_hingejoint3d.html)、[ConeTwistJoint3D](https://docs.godotengine.org/en/stable/classes/class_conetwistjoint3d.html)
- **阻尼**决定“摆动多久、速度衰减多快”。增加角阻尼不能阻止膝盖反向折叠，也不会把已折错的身体恢复成人形。当前还需考虑阻尼模式及项目默认阻尼的叠加，不能只读控制器的 0.25 就当成最终总阻尼。
- **姿势驱动**决定“是否主动朝某个目标姿势回正”。被动物理身体在重力下塌落是正常的，但仍应符合关节和身体体积限制。如果关节和碰撞合格后，美术仍希望胸颈稍微保持形状，可再加入小强度、有最大力矩限制的姿势驱动；不必立即开发站立平衡、自恢复等完整 active ragdoll。ezEngine 的 Jolt 官方集成文档也明确区分 limp、powered 与 controlled；这只是控制策略参考，不能把其组件 API 直接复制进 Godot。[ezEngine：Jolt Ragdoll Component](https://ezengine.net/pages/docs/physics/jolt/ragdolls/jolt-ragdoll-component.html)

现阶段优先补活动范围和体积，再调阻尼；需要额外形状保持时才增加局部姿势驱动。不要通过重开整链速度牵引、锁死所有骨骼或恢复世界 Y 缓冲来“变硬”。

### 8.3 必须写对的 PhysicalBone3D 参数与单位

**PhysicalBone3D 的动态 `joint_constraints/...` 角度属性使用度。** 不要因为独立 Joint3D/PhysicsServer3D 接口使用弧度，就对这套属性再调用 `deg_to_rad()`。读取运行时属性列表和读回值核对；当前运行时读到 CONE 的 45/180，也与 Godot 源码动态属性的度/弧度转换一致。[Godot PhysicalBone3D 实现](https://raw.githubusercontent.com/godotengine/godot/master/scene/3d/physics/physical_bone_3d.cpp)

下面只是给实施 agent 的参数示例，**未应用到项目，且前提是关节坐标系已校准**：

```gdscript
# PhysicalBone3D 动态属性；例：肘部或膝部的工程起点。
# 先设类型，再设该类型的属性；左右侧方向需分别校准。
pb.joint_type = PhysicalBone3D.JOINT_TYPE_HINGE
pb.set("joint_constraints/angular_limit_enabled", true)
pb.set("joint_constraints/angular_limit_lower", 0.0)
pb.set("joint_constraints/angular_limit_upper", 135.0)

# 例：躯干分段，先限制夸张折叠和扭转。
pb.joint_type = PhysicalBone3D.JOINT_TYPE_CONE
pb.set("joint_constraints/swing_span", 20.0)
pb.set("joint_constraints/twist_span", 15.0)
```

两个示例代表不同关节，不应顺序应用到同一个部位。`joint_constraints/angular_limit_enabled` 是 PhysicalBone3D 的路径，不是独立 HingeJoint3D 的 `angular_limit/enable`。Hinge 改类型后默认并不自动启用限角，必须显式打开。动态属性还应检查 `set()` 是否成功、读回值是否符合预期，不要只设置一个不存在的路径。[PhysicalBone3D 默认与参数定义](https://raw.githubusercontent.com/godotengine/godot/master/scene/3d/physics/physical_bone_3d.h)、[Hinge 限角启用条件](https://docs.godotengine.org/en/stable/classes/class_hingejoint3d.html)

工程调试起点可用下表，**这些是拟议的视觉调试值，不是人体医学范围或已经验证的最终参数**：

| 部位 | 优先方案 | 工程起点 |
| --- | --- | --- |
| 膝、肘 | HINGE + 显式限角 | 约 0–135°，按实际弯曲轴确定正负与零点，禁止反折和侧折 |
| Spine、Chest | 有限 CONE | 摆动约 15–25°、扭转约 10–20°，逐段检查累计弯曲，不能每段都给整条脊柱的活动量 |
| 头颈 | 有限 CONE | 摆动约 20–30°、扭转约 30–45°，避免头部向后翻折；根据颈部骨架与模型单调 |
| 肩髋 | 有限 CONE；不够表达时再评估 6DOF | 先保留比躯干更大的摆动、显著缩小默认 180° 扭转；圆锥本身不等于各方向不对称的人体活动范围 |
| 脚踝、手腕 | 小范围 CONE 或适当限轴方案 | 先限制翻转和连续扭绕，具体轴向随当前绑定校准；不继续保留完全自由 PIN |

不要把表格数值直接套到未校准的关节：骨骼轴、胶囊长轴和关节的扭转/弯曲轴未必相同。先看静止姿势下关节标记，再做单关节正向、反向和侧向施力检查；左右镜像可能需要翻转轴或范围符号。初始姿势若已超出限角，启动时会被求解器猛烈纠正，表现为弹飞、抽搐；这属于坐标系/初始条件错误，不能靠加阻尼压下去。

Jolt 对部分 bias/softness/relaxation 等参数不支持，调这些不能替代真正的角度限制。先使用支持的关节类型、范围与正确坐标系，再考虑求解精度或关节驱动；不是“Jolt 只能使用 6DOF”。[Godot 官方 Jolt 参数兼容性](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)

### 8.4 碰撞体不能全部以关节为中心

最新代码把所有胶囊中心改成 `Vector3.ZERO`。对于以近端关节为骨骼原点的长骨，这会让胶囊沿骨段向两端各伸一半，不能覆盖预期的整条可见肢体；也把质量分布、支撑位置和相邻形状交叠集中到关节附近。**零 body_offset 或 joint_offset 本身不是必然错误，但“所有部位同一套零偏移”不能代替拟合。**

建议从静止骨架中取近端与远端，选择合适的局部轴与骨段中点设置物理身体/形状，关节仍落在实际关节处。若移动物理身体中心，须配套维护 body_offset 和 joint_offset，保证可见骨骼、刚体与连接点一致，不能只把胶囊视觉上挪开就结束。躯干、头、手脚分别拟合，不用同一种骨段胶囊强行覆盖全部部位。

限角正确后，逐步允许必要的非相邻部位自碰撞，例如前臂与躯干、左右腿；明确排除相邻连接部位，并检查初始交叠。当前直接把 mask 从 1 改成 5、开启所有部位互撞，可能让中心错放、互相交叠的胶囊立即爆开。项目以后存在多个角色时，还要区分“同角色相邻排除”和“不同角色之间的碰撞策略”，不能仅靠共用层号表达全部规则。

### 8.5 给实施 agent 的顺序与交付要求

1. 保留已修好的 16/16 绑定。在原沙盒内先停止拖拽干扰，校准静止骨架、身体中心、关节锚点及 15 条预期连接。
2. 先做一个膝关节和一个肘关节的轴向与限角；通过后镜像到另一侧，再分配躯干、头颈、肩髋、手脚范围。不要一次改所有角度后只看“感觉”。
3. 逐对开放必要的自碰撞，排除邻接对；比较静置和抬起单个部位时是否仍穿过躯干。再调适量阻尼与休眠，避免反复摆动。
4. 恢复单点拖拽测试。当前仍是骨骼原点的速度跟随，应继续向真实局部抓取点的受限力/约束收敛；抓取目标要限制突变，不能用硬拉速度掩盖关节或拖拽失稳。
5. 若仍需视觉上更有支撑，只对确有需要的胸颈等部位增加弱姿势驱动，肢体保持自然随动；先不增加全身平衡或自动站起功能。
6. 在**原验证脚本**追加：16/16 状态、限角已启用及读回值、每个关节活动方向、连接锚点误差、身体自交与身体/家具接触。位置锚点误差和允许的关节旋转应分别判定：正常折肘不是断骨，连接点明显拉开才是约束失效；若是后者，应检查关节是否实际建立、受力和质量/求解问题，不能靠角阻尼解决。

验收目标是“放松但有骨骼和体积”：抓一侧手脚时其他部位能滞后摆动，膝肘不反折、颈椎和腰部不拧成结，身体不互相穿成一团；松手后能自然落地安定。允许塌落，不要求保持动画站姿；同时不能再退回整个人像一块板。
