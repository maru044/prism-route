# CPU / GPU 瓶颈排查 · 2026-11-02

结论：瓶颈随视角变化。覆土庭院入口主要受草地 GPU 渲染限制；洞口 GPU 负载较小时，水面反射对象管理成为明确的 CPU 瓶颈。没有证据表明是整个项目统一从 GPU 转为 CPU 受限。

**优化已完成。** 以下前半部分保留优化前诊断，文末记录正式代码改动、回归验证和新旧代码在同一运行实例中的对照。

- 开发机 Intel Core Ultra 7 265KF、RTX 5070 Ti。
- 单独的自动化运行，固定镜头，先预热并等待草块加载；对照阶段关闭 60 FPS 上限及 VSync，避免帧率上限掩盖余量。
- 每个对照采样约 3 秒，变化前后都恢复基线；脚本回调用临时诊断驱动计时，存在少量测量开销。该结果适合热点归因，不是最低配置承诺或正式发行版本跑分。
- 未更改项目渲染设置、植被密度或树木存档。临时探针位于 `.current_map_build/cpu_probe_1102/`；原始采样副本随本文保存。

## 已定位的 CPU 热点

`scripts/water/water_manager.gd` 当前登记 5,666 个代理，其中动态代理数为 0。

1. `_process()` 每帧调用 `_update_tree_proxies()`，对整个数组检查实例有效性和场景树归属，包括大量始终不变的静态建筑与树木批次。
2. 反射启用时，每 0.25 秒再次遍历整个代理数组，更新可见性和视距。视角静止时仍重复执行，增加周期性尖峰。
3. 第一轮计时中水面管理约 4 ms / 帧，部分帧超过 10 ms。第二轮固定画面的数组对照，使该模块降至约 0.04–0.09 ms / 帧，洞口帧时间减少约 4 ms。

最近持续增加建筑和反射对象，会继续放大这套全表巡检的代价。不过没有对旧提交做相同条件的基准，不能把全部变化归因于最后一个建筑。GPU 工作量随视角减少时，原本已经存在的 CPU 开销更容易显现。

## 草地及其他模块

第一轮入口完整加载后：328 个常驻草块，排队及近处待加载为 0，烘焙缓存有效且损坏计数为 0。草地流加载脚本约 0.17 ms / 帧，风力 / LOD 更新约 0.19 ms / 帧；冻结这两部分没有显著改变约 10.2 ms 的稳态帧时间。冷加载阶段会出现较高上传和解码开销，需要与稳态区分。

仅隐藏草的诊断对照，使主视口 GPU 从约 9.65 ms 降至 2.94 ms；3D 渲染比例降为一半后 GPU 约 7.01 ms、帧时间约 8.00 ms。因此入口仍有明显的草地 GPU 成本。本次没有据此减少草量或画质。

音频、角色脚本、全息参数更新等的平均调用耗时明显小于水面代理管理。物理监视器也不是平均物理帧耗时，不能把其数字直接与手动测出的脚本平均值相加。

## 面板口径导致的误读

当前面板“引擎处理 / 物理”直接读取 `Performance.TIME_PROCESS` 和 `TIME_PHYSICS_PROCESS`。

核对当前引擎版本源码后发现，Godot 将一段约 1 秒统计区间内的 `process_max` / `physics_process_max` 写入这些监视器，随后清零；处理计时也包含渲染同步和绘制调用。因此它不是“每帧平均纯 CPU 脚本耗时”。例如第一轮入口锁 60 FPS 时，实际平均帧间隔约 16.63 ms，而这个监视器平均读到约 24.40 ms 的区间峰值，两者并不矛盾。

面板“渲染 CPU / GPU”是主视口的渲染计时，也不是完整 CPU 预算：总 CPU 渲染还需要考虑其他视口及 `RenderingServer.get_frame_setup_time_cpu()`。脚本、原生场景管理与物理应单独计量，避免混用平均值、区间峰值和不同流水线阶段。

来源：[Godot 4.7.2 主循环源码](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L4723)、[RenderingServer 计时说明](https://docs.godotengine.org/en/latest/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu)。

## 诊断时建议

优先处理静态反射代理的重复巡检，将注册 / 删除、编辑器动态对象维护与视距筛选分开；固定场景和静止视角避免每帧进行相同的全量检查。保留植物编辑、撤销、显隐和水面反射正确性，再用本文相同镜头复测。随后修正监视面板标签，明确“约 1 秒区间峰值”和真实分项平均耗时。以上为优化前诊断；实际实施结果如下。

## 已实施的优化与验证

### 正式代码

- `scripts/water/water_manager.gd`：静态代理依靠源节点退出 / 显隐信号更新，取消每帧 5,666 条有效性巡检。删除用索引交换移除，筛选快照内的旧记录先标记失效，避免撤销、换区或延迟删除产生已释放实例引用。重复注册不会累积代理。

### 性能验收

全部 18 个预设镜头复测，原始结果 `optimized_results.json`：静止时水面 `_process` 平均约 **0.04–0.10 ms**。所有固定镜头采样结束时草块排队为 0；另有移动镜头样本包含正常流加载，不能视作静态对照。

移动镜头在出生洞口附近以正弦轨迹横移，最大速度约 10 m/s：

| 条件 | 水面 CPU 均值 ms | P95 ms | 最大 ms |
| --- | ---: | ---: | ---: |
| 解除帧率上限，6 秒 | 0.10 | 0.47 | 0.63 |
| 60 FPS + VSync，5 秒 | 0.47 | 0.60 | 0.94 |

达到了平均小于 0.5 ms 的目标。0.4 ms 是距离筛选循环的目标预算，不是整个水面管理回调的硬上限；新增 / 显隐 / 动态更新与材质参数写入也计入总耗时。

18 地点巡检后半程有总帧时间波动，而水面耗时仍低。因此额外进行了同一实例的新 → 旧 → 新对照，避免把不同运行轮次的 GPU / 帧间隔波动归因于代码修改。临时加载 `aa92ff0` 中的原始管理脚本，交替驱动同一组代理节点、材质、反射视口及镜头，没有创建第二份反射场景；详见 `paired_results.json`。

| 固定镜头 | 旧代码帧时间 ms | 新代码前 / 后 ms | 水面 CPU 旧 → 新 ms | 主视口 GPU 旧 → 新后 ms |

| 出生洞口 | 8.16 | 3.16 / 3.18 | 4.42 → 0.04 | 2.86 → 2.83 |
