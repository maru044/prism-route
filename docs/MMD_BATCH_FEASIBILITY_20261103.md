# MMD 动作库批量移植调研与实施计划

日期：2026-11-03。适用项目：Prism Route；当前目标：刻晴、甘雨既有 VRM。

**后续范围修订：角色将有几十个，正式资源应采用共享人形动作库，而非逐角色逐动作烘焙。见第 11 节。** 下文两种目标全覆盖的成本仅是现有样本方法的量级说明，不是几十角色的推荐生产架构。特殊动作可暂缓，先选择实际需要的少量动作；长动作按需截取，不为源库约 400 MB 专门裁剪。

**最新实测：共享层已完成三份动作 × 四个 VRM 的验证，没有新增目标专属动作或 Blender 烘焙。** 结果与后续制作入口见 [共享人形动作规范](MMD_SHARED_HUMANOID_VALIDATION.md)。原成本表保留作样本方法对照，不作为共享库的新预算。

**选片入口已实现：** [Blender 源动作选片器](MMD_SOURCE_PREVIEW_GUIDE.md) 可直接浏览源库并记录保留片段；先选择实际需要的动作，再安排批量制作。

**结论：现有路线可以批量化，适合先产出身体动作基本正确、双人同步、复用实时头发和服饰物理的预览库。现有脚本仍是 Loop 03 样本工具，不能直接遍历目录后把所有输出标为完成。**

212 个人体 VMD 包含 194 份不同的骨骼与 IK 数据。其中 **175 份（90.2%）未发现当前两套 PMX 代理缺失必要主干或手臂控制骨，可进入常规试跑队列**；19 份需特殊处理。这是静态兼容性分流，**不是 90.2% 成品成功率，也不是 175 组完整双人动作**。配套、模型比例和接触位置仍须整组验收。

建议首批优先普通/FK 版本，暂缓无法还原的特殊 IK、未确认多人组、道具和完整表情复现。允许少量发丝/衣摆穿插、手指和表情差异；漏角色、明显错误的手臂、失同步和严重空间错位不能作为“小问题”忽略。

## 3. 兼容性分流

检查的是“VMD 能否被目标角色对应的 PMX 代理接收必要控制信息”，不是直接把 VMD 名称写到 VRM。

| 口径 | 人体原文件 / 212 | 去重骨骼+IK / 194 |
| --- | --- | --- |
| 仅检查变化的标准主干/肢体/手臂 IK | 201 | 185 |
| 加上固定非默认控制姿态、手臂 `+` 扩展骨 | **190** | **175** |
| 存在上述必要控制骨缺失 | **22** | **19** |

两套代理骨架在这一分流上相同。采用第二行作为常规候选口径。部分 IK 目标始终不变，却仍决定手臂姿态；只统计多关键帧或动态骨会高估兼容性。

其他结果：

- 未检测到非有限数值、未解析尾部、损坏骨名编码或非零人体起始帧。
- 53 个 VMD 含重复的同骨同帧记录，但未发现内容冲突。可确定性去重并回归检查。
- 3 个人体文件有脚/脚尖 IK 开关切换，位于 Reverse Stradle 和 Stand and Carry 两个版本目录；必须完整求解后再烘焙。
- 202/212 个人体 VMD 带 Morph 数据，其中 158 个出现过非零权重。当前身体方案没有迁移这一层，不能声称原动作没有表情。
- 还存在作者模型专有的形变、局部细节及辅助控制骨。细节可降级；承担主姿态或显隐功能的依赖须转特殊队列。

**175 份是试跑候选上限，不是已完成成果数。** 一人的轨道可转、另一人依赖特殊 IK 时，不能将单人成功算为完整配套成功。

## 4. 不能忽略的问题

### 特殊手臂 IK 与跨角色 External Parent

作者明确要求外部父级或加载/计算顺序的身体动作目录有 **6 个：Loop 28、32、33、34、35、38**。另有两份重复的道具说明涉及外部父级事件。

它们可能将一人的控制器绑定到另一人的头、躯干或腿。VMD 不携带完整控制骨层级和所有跨模型关系。当前 PMX 代理没有这些作者特有的手臂 IK/`+` 控制骨；**忽略缺失骨后导出文件不等于正确完成动作**。

22 个特殊人体文件中，有 **9 个“同目录、同模型族、相同结束帧”的普通版本替代候选**：Loop 21、22、24、32、33、34、35、38，以及 Pink lounge 更新 1.1 的其中一段。仍需整组抽查确认演出版本一致。

Loop 23、28、29、37 等没找到同目录同条件的普通候选；Stand and Carry 两个伙伴版本也不能直接推断有 FK 替代。其他版本目录可能有替代，须按片段确认。

优先普通版本，没有时整组暂缓。完整支持需获得原作者控制骨架或重建并验证等价控制器，在同一个 Blender 场景建立双方依赖、遵守求解顺序，再分角色输出。不能将 IK 骨名简单改成普通手臂骨名。

### 人数、配套与替代版本

**Loop 27 有 Izumi、Rin、SinSack 三份不同角色的人体轨道，均为 0–2000 帧**，应列为三人候选核实，不能自动丢掉第三条。

Motorcycle Photoshoot 2nd pose 有两条 0–1615 动态人体轨道和第三角色的第 0 帧固定姿态。第三份可能是场景角色或替代安排，不能删除，也不能未经审核当成三人组。

反过来，许多目录的 Maran / SinSack 是同一角色位的模型替代；Short Loops、Extra Loops 在同目录放了多个片段。模型头标签也不可靠，部分被 20 字节限制截断。

现有 Godot 场景按 `roles` 列表生成实例、共用时间，但碰撞位掩码仍按 A/B 写死，分类和验证围绕双人。需补人数和角色位元数据。三人技术上可用已有两种 VRM 配置创建第三实例，角色分配与视觉适配另行确认；首批可暂缓三人候选。

### 双人接触与模型比例

VMD 没有完整保存原作者模型骨长和静止姿势。当前方案在各目标自己的 PMX 代理求解，再转到其 VRM，能保证链条一致性；不能保证不同身高、臂长仍精确接触。

Loop 03 已有机制证据：共同时间误差 0；源关节比较最大约 `8.8e-7 m`，双方相对关节向量最大约 `1.3e-6 m`；共 41 条物理链，30/60/120 FPS 通过现有机制测试。**画面仍有局部服饰重叠，未获最终接触适配批准。**

保留坐标与同步保证移植没有破坏原始关系，不能替代体型适配。对方碰撞只影响头发/服饰，不移动身体，也不替手臂做接触 IK。初版容忍轻微手指/布料偏差；明显悬空、手臂错位、大面积身体相交应返修或暂缓。修正保存为组级偏移、角色位适配或接触 IK，不能双方分别居中。

### 帧范围与循环

14 个多轨父目录内有不同结束帧，既有尾差，也有混放片段/替代版本，不能统一截最短或每条独立拉伸到同长。

- Loop 05 为 609/610，一帧差可在确认配套后保持短轨末姿态。
- Loop 08 为 1002/1372，须先确认片段关系。
- On the floor 作者指定循环 **0–2497**，身体文件结束在 2529/2650，不能整段强制循环。

一组使用同一绝对时间；分别记录源轨长度、演出范围和循环范围，保留事件和过渡。全库起始帧虽都是 0，未来也不能写死这一假设。

### 相机、道具、表情与其他格式

43 个相机、24 个道具/辅助、2 个服装姿态、4 个 Morph-only VMD 必须分型。首批使用身体预览和通用观察相机；家具/支撑依赖标为 `requires_prop`，不能声称完整场景已还原。

RCG 作者要求两人母骨共同沿源 MMD Y 轴移动 7.90 个源单位以匹配相机。这是组级规则，不是各自归零，也不是直接在 Godot 移动 7.90 米。

5 个 MVD 均能在相同来源组找到 VMD 候选：两组 Motorcycle Photoshoot 和 Nice rear view。首批跳过 MVD、选 VMD 候选可行，**未证明内容完全相同**。当前链条不直接支持 MMM MVD。PMM、EMM、声音、相机和表情完整还原另设阶段。

## 5. 现有方案复用与必要整理

保留已验证路径：

```text
分型与组清单
 → 对应 PMX 代理 + VMD（保留 IK / 追加变换求解）
 → Blender Visual Bake，得到无约束骨架
 → 活动场景、选中骨架的 GLB
 → 源世界姿态 × inverse(VRM 原节点世界静止姿态) × Godot 导入世界静止姿态
 → 每目标配置的身体 Animation + 共享 VRM / Spring Bone
 → 同一 Godot 场景、组时钟播放与验收
```

每角色配置保存源 PMX、目标 VRM、Godot 静止骨架、名称/轴向修正、物理骨排除表及物理/碰撞配置。新角色须独立建配置，不能复用刻晴骨长或物理骨名单。

| 当前实现 | 批量前所需修改 |
| --- | --- |
| Blender 固定路径、对象名和 0–480 帧 | 从任务 JSON 读取配置/范围/路径，支持静态姿态与长动作 |
| A/B 重定向分别实现，B 固定 16 秒/481 点 | 公共转换函数，采样与参考帧由任务决定 |
| 物理构建与单动作构建耦合 | 每角色生成一次物理 VRM，所有动作共享 |
| 全身体骨逐帧位置/旋转 | 折叠常量轨；动态轨按误差约束优化并回归 |
| 选择器标注 `*.tres` | 若改二进制 Animation，补 `.res` 保存/加载验证 |
| 测试固定 Loop 03 帧/角色/参考 | 按组验收，长片段抽样加事件帧，失败隔离 |
| A/B 碰撞分层 | 扩展人数/碰撞配置，或首批明确限制已确认一/二人组 |
| 一组 catalog | 生成 pack/role/variant 清单、稳定 ID、状态和依赖 |

保留既有经验：不能把 VRM inverse-bind 当作原节点静止姿态；不能提前清源约束；GLB 同时限制选中对象与活动场景；物理骨不再写身体轨道；Spring 复制保留碰撞组资源身份；物理验收走引擎真实帧进程。

## 6. 任务化与缓存方案

按**完整演出组**组织，角色轨道作为转换作业。

| 层级 | 必需元数据 |
| --- | --- |
| Pack | ID、来源、人数、FPS/公共范围/循环段、坐标策略、依赖、审核状态 |
| Role | 角色位、VMD/哈希、目标配置、替代版本/固定姿态标志、缺失控制骨 |
| Dependency | 外部父级/求解顺序、道具支撑、作者偏移、Morph 显隐 |
| Build | 输入/代码/工具版本哈希、分段耗时、退出码、输出哈希、失败阶段 |
| QA | 结构/数值/同步/物理/视觉分别记录状态 |

缓存键至少包含源骨骼/IK、源 PMX、目标骨架/导入设置、采样设置、转换器版本；跨角色约束再加入整个依赖组与角色分配。Morph 单独管理，不能因骨骼相同合并表情版本。

本次 194 份去重只是骨骼+IK 字节相同统计；相机、Morph、道具及外部绑定不同，完整演出仍可能不同。

用 **Blender 后台 CLI** 执行，保留交互 Blender。先一个 worker，逐组/小批运行，支持超时、日志、退出码、断点和有限重试。不要靠一个实时会话累计导入几百份动作。复用源骨架时必须重置动作、IK、Morph、NLA，清理孤立 Action，每任务重新初始化。

发布时模型/物理共享，动作按需加载。继续用现有独立验证场景，不把整个库同时常驻或放入主地图。

## 7. 资源成本与耗时预期

### 输出冗余与空间

| Loop 03 单角色 16 秒 | 刻晴 | 甘雨 |
| --- | --- | --- |
| 文本 Animation | 7,843,371 B | 9,043,517 B |
| 轨道数 | 288 | 326 |
| 逐帧关键帧 | 138,528 | 156,806 |
| 偏离首值不超过 `1e-5` 的常量候选轨 | 246（85.4%） | 280（85.9%） |

位置按向量差检测；四元数归一化并消除正负号等价，再比较分量距离。此阈值不是角度或压缩验收标准。

**常量轨保留一个正确姿态键，不能直接删掉**，因为它可能不是静止值。切换动作完整重置，避免继承上一动作。优化后比较原输出，不能只验键数。

按现有样本每采样点体积线性外推，194 份数据都为两种角色各输出一次，约 388 个“数据 × 目标配置”作业：身体 `.tres` 约 **11.8 GB**，GLB 中间动画约 **8.4 GB**，合计约 **20.2 GB**，尚不含 Blender 工程、参考、导入缓存和余量。

这是未优化量级估计，其他动作的变化、文本数值长度和范围会影响结果。每源角色轨只分配一个目标时，通常更接近一半，取决于角色分配与特殊组上下文。**首批按角色位生成实际需要的版本，避免无需求全排列。**

优先常量折叠，试验并验证二进制/压缩存储；不能把样本 85% 常量轨直接宣称为全库 85% 体积收益。模型/物理复用，不为每条动作复制约 29 MB 的 VRM。

### 内存与并发

本次快照：20 个逻辑处理器；物理内存约 31.6 GiB，当时可用约 7.5 GiB；D 盘空闲约 70.5 GiB。可用资源会随其他程序变化。

最长 7680 个采样点。若约 315 骨都逐帧输出位置、四元数与缩放，中间动作理论上约 2400 万个标量键值，另有曲线、句柄、依赖图与导出缓存。先用长样本测内存峰值，**初期 1 个后台 worker**，测量后决定是否升至 2 个，不能按 CPU 线程数开并发。

中间产物放研究/工作目录；发布只留必要资源，不默认保留每任务的完整未压缩 `.blend`。

### 耗时与排期

对现有刻晴 GLB 做 3 次、每次 41 个时间点的原重定向数学测试，约 **8.6 ms / 点**，包含 GLB 姿态、世界矩阵和轴向重定向，排除 Blender、写盘和 Godot QA。

这一部分线性外推约 **0.8 小时 / 一套目标**，两套约 **1.6 小时**。这是局部算术量级，**不是全流程完成时间或严格下界**；目标骨数、长动作、调度和未来优化都会改变结果。

全流程用试跑实测的“启动/导入固定成本 + 每点成本 + 导出/验收”估算。以下仅为敏感性示例，单价均是假设，未实测到这些端到端速度：

| 每 481 点摊销端到端成本（假设） | 每数据分配一个目标的近似量级 | 两种目标全覆盖的近似量级 |
| --- | --- | --- |
| 30 秒 | 5.8 小时 | 11.6 小时 |
| 60 秒 | 11.6 小时 | 23.2 小时 |
| 120 秒 | 23.2 小时 | 46.5 小时 |

特殊组和人工接触适配不含其中。当前应按稳定长任务/断点恢复设计，不能承诺几分钟全转完。代表试跑后再给可信总工时。

## 8. 允许问题与失败边界

| 结果 | 初版处理 |
| --- | --- |
| 少量发丝/衣摆穿插、手指偏差、部分表情缺失 | 带警告进预览库，记录限制 |
| 一帧尾差、内容完全一致的重复键 | 统一保持/去重规则，回归配套节奏 |
| 跳帧后物理收敛、帧率间小差异 | 保留复位和真实帧验证，不要求物理逐帧完全一致 |
| 缺必要手臂控制器、多人少放角色 | 暂缓整组，不能用单轨成功替代 |
| 独立缩放时间、双方各自居中、严重错位 | 失败，修复坐标与组时间 |
| 严重相交、丢失关键接触/支撑 | 返修或暂缓 |
| 家具/支撑物未提供 | 身体预览可留依赖警告，完整场景不通过 |
| 数值异常、骨轴爆炸、损坏、持续发散、内存失控 | 失败隔离，不阻断其他独立组 |

首批不必每条都精修，也不能为追求全绿隐瞒角色丢失或控制器缺失。

## 9. 分阶段实施计划

### A：清单与工具整理

从调查表确认一/二/多人、普通/IK 替代、片段范围和依赖。抽公共转换器、角色配置、后台作业、日志缓存；去掉 480 帧限制。先做常量折叠与切换完整重置。

完成门槛：同一任务 JSON 驱动 Blender → 重定向 → Godot 验收；失败可续跑；不覆盖原始文件。

### B：约 10–12 个来源组的代表试跑

| 样本 | 目的/预期 |
| --- | --- |
| Loop 03 | 已有双人基线回归 |
| Loop 05 | 一帧尾差与短轨保持 |
| Loop 08 | 大长度差，先确认组关系 |
| Loop 21 或 32 普通版 | 普通版优先、IK 版正确分流 |
| Reverse Stradle | 脚部 IK 状态随时间求解 |
| On the floor | 作者循环段与不等长轨 |
| Just Tonight 完整版 | 7030 帧长片段，测峰值内存/分段耗时/断点 |
| Loop 27 | 核实三人，支持第三角色或明确暂缓 |
| Motorcycle Photoshoot 2nd pose | 静态第三角色候选、零时长姿态保留 |
| Nice rear view | Morph/场景轨与 MVD/VMD 替代分型 |
| RCG | 作者组偏移；首批不强制复原相机 |
| Loop 28 或 37 | 无明显普通替代时正确暂缓，不能误报通过 |

这些是建议试跑，**本次没有转换它们**。未支持组正确报告暂缓也是验收内容。记录每样本源/目标、帧数、分段耗时、峰值内存、大小、缺失控制器、数值/同步/物理/接触结果。

### C：常规队列批处理

从 175 份静态候选中按已确认组和角色位选必需轨道，先不做目标全排列。逐组作业、缓存续跑、失败隔离；生成现有独立场景读取的动作库目录，按需加载。

结构/数值检查覆盖每个产物；完整物理帧率回归覆盖代表和有问题的动作；每配套组做简短整组视觉检查，复杂接触标返修，不能只看单人。

### D：例外与质量提升

再处理 19 份特殊控制数据、三人、支撑物、相机/音频及必要 Morph，按实际用途排序接触修正。物理配置因新动作修改后回归代表组，不为每动作复制 VRM。

建议状态：`candidate → grouped → built → technical_pass → preview_ready`，另设 `needs_contact_fit`、`deferred_dependency`、`failed`。不能一个 `passed` 同时代表数值、物理和美术完成。

## 10. 结论与复现

**建议推进“常规先覆盖，特殊依赖隔离”的批量原型。** 文件损坏不是本库主要障碍；控制骨、组关系、多人、接触比例和长动作资源才是重点。新增工作主要在清单/分流、任务化、存储优化与整组验收。

预期能形成可浏览筛选、身体动作基本正确、带实时物理的库；没有证据支持全部素材无需人工即可达到最终接触质量。允许小问题有助首批推进，不能替代必要依赖与角色完整性。

在项目根目录复现（Python + NumPy，本机骨名快照与 MMD Tools）：

```powershell
python tools/audit_mmd_motion_library.py
python tools/research_mmd_batch_costs.py
```

第一条重建静态调查，第二条读取现有验证资源、测量数学部分并复核原版 Reader，均非批量转换入口。类型为启发式识别，组关系仍须审核；新增动作或更新模型/工具后重新扫描和回归。

相关规范：[MMD → VRM 制作指南](MMD_TO_VRM_PRODUCTION_GUIDE.md)、[配套动作验证规范](MMD_PAIRED_MOTION_VALIDATION.md)。既有机制报告：[verification.json](validation/mmd_pair_loop03_20261103/verification.json)。

## 11. 几十个角色时的正式方案：共享动作，角色一次适配

用户确认将有几十个角色，因此正式架构不继续使用“每个动作 × 每个目标角色都离线烘焙”的资源矩阵。现有刻晴/甘雨结果作为精确转换与物理机制的回归基线保留。

### 本机核对结果与边界

已读取项目内甘雨、刻晴、胡桃、花火四个 VRM（后三者为 import_tests_local 的 fixed 版本）：四者均声明 53 个 humanoid 骨骼映射，所检查的主干和四肢均完整。它们的原节点总数为 278、278、252、720，说明非人形辅助骨差异很大，不能把全部骨骼当作统一接口。此项只是这四个文件的结构检查，不代表其他几十角色已验证，也不代表动作外观已一致。

项目现有 VRM 导入器 `addons/vrm/importer/common/vrm_skeleton_retargeting.gd` 已有标准名称、SkeletonProfileHumanoid 轴向修正和按髋高设置 motion_scale 的处理，具备共享人形动作所需基础。但样本播放脚本将 motion_scale 设为 1，样本动画包含绝对局部位置和角色专属非人形骨；这些 `.tres` **不能直接当作通用库挂给所有角色**。不能只重命名轨道就宣布迁移完成。

### 资源划分

| 层级 | 制作与复用方式 |
| --- | --- |
| 通用身体动作 | 每条源角色轨道在少数参考控制骨架上完成求解，提取标准人形姿态，存一份共享资源；不按最终角色重复进 Blender |
| 角色适配 | 每个 VRM 接入时提取一次人形映射、静止姿态/轴向、比例和必要辅助骨规则；新角色通常无需提供 PMX |
| 角色物理 | 每个角色/服装保存一次自己的头发、服饰、碰撞配置；所有动作复用，不能跨角色照搬骨名和半径 |
| 配套演出 | 共享角色位轨迹、时间和动作角色位；必要时按体型类别或少数重点演出增加接触修正 |

标准化时保留目标自身骨长，传递人形骨旋转及有明确尺度约定的髋/根位移；原控制骨、扭转骨和中间父骨的作用须从求解后的姿态折算，不能直接复制原局部四元数或把所有局部位置写给目标。映射外的骨交给角色辅助规则或实时物理。

实现可以使用标准骨架动画资源，也可评估 VRMA 作为交换格式；文件后缀不是通用性的保证，必须验证实际导入和姿态语义。角色接入的静态校正与运行时姿态应用仍有计算成本，但无需重复烘焙并发布大量角色专属动画；若采用按需生成 Animation 的过渡实现，也应作为可丢弃缓存，而非正式资源全排列。

### 接触与范围策略

走路、待机和普通肢体动作适合广泛共享；双人动作可以共享角色位动画，但不同臂长/身高仍影响手脚接触。单人可按身高调整的位移策略不能直接用于配套组的全部轨迹：双方各自缩放世界坐标会破坏关系。配套需要共同坐标约定，必要时组级适配或接触 IK。

初版不追求所有角色组合的精确接触。先选体型相近角色支持常用配套，体型差异明显时警告或限制组合，避免扩张到角色组合数的手工修正。特殊控制器、缺失必需骨、严重错位依旧暂缓。

### 下一次实施前的验收门槛

先用一条普通动作和一组配套动作验证：同一共享动作资源在刻晴、甘雨、胡桃、花火上播放，不为四个目标分别进入 Blender 烘焙；检查骨长没有被源动画覆盖、髋高和位移正常、角色切换无残留姿态、配套时钟和世界坐标一致。物理分别使用角色自身配置，接触质量单列。

上述共享层**现已实现并完成四模型样本验收**，详见 [实测记录](MMD_SHARED_HUMANOID_VALIDATION.md)。下一步选取约 10–20 组实用动作小批制作。工作组织从“角色数乘动作数的重复制作”改为“动作标准化 + 角色一次适配 + 少量必要例外”，不能把适配配置的维护误解为完全零工作。
